# ADR-0003：卡牌内容以类型化 TS 常量驱动，而非 JSON / YAML

## 背景（Context）

卡牌是本项目的主体内容，规模会从几十张长到数百张。每张卡包含：id、角色、正文、左右两个选项、
每个选项对四指标的效果、出现条件（指标区间 / 标记）、权重、是否一次性。
这些字段多且互相约束（例如「选项效果不能全为零」），一旦写错，运行时才会暴露。

## 决定（Decision）

卡牌与结局定义在 `src/content/` 下，用 **TypeScript 常量数组 + `satisfies`** 表达：

```ts
export const CARDS = [ /* ... */ ] satisfies readonly Card[];
```

- 类型定义全部来自 `src/core/types.ts`，内容与类型单一事实源。
- 用 `satisfies` 而非类型注解：既获得完整类型检查，又保留字面量类型（便于按 id 精确索引）。
- 结构约束（双选项、效果非零、id 唯一、至少一张兜底卡）由 `src/core/__tests__/content.test.ts` 在 CI 中强制。

## 被否决的备选及原因（Alternatives considered）

- **JSON 数据文件**：编辑门槛低、可被非代码工具处理。
  否决原因：失去编译期类型检查，字段写错（如 `civilian` 拼成 `civilians`）要到运行时才炸；
  需要额外写 loader 与校验层，等于把 TS 已经免费给的东西重造一遍。
- **YAML / Markdown 前置元数据**：人类可读性最好，适合大量纯文本创作。
  否决原因：同样失去类型检查，且需要引入解析依赖与构建期校验脚本。
  若未来内容创作量大到需要非工程同学参与，可重新评估并新开 ADR 加一层「YAML → TS 生成」的构建步骤。
- **硬编码进组件**：开发初期最快。
  否决原因：直接违反不变量 #4；内容规模上去后无法批量校验与做平衡统计。

## 后果（Consequences）

- 正面：字段拼写、类型、必填项在 `npm run build` 阶段就被拦截；IDE 补全让写卡更快；
  完整性守卫测试可在 CI 里跑，不依赖运行时。
- 负面：内容文件是代码，非工程同学编辑门槛高；内容改动也会触发 lint / 测试流程。
- 后续要注意：内容文件应保持「纯数据」——出现任何函数或控制流，就说明该逻辑属于 `src/core/`，应下沉。

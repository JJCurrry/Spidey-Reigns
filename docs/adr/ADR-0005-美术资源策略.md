# ADR-0005：美术走 AI 生成 + 资源清单协议，不硬编码进逻辑

## 背景（Context）

视觉是《Reigns》体验的一半：角色立绘、卡面质感、四指标图标、结局插画。
本项目没有专职美术，也没有稳定素材管线，而内容量（数十个角色、数百张卡）要求资源必须可批量替换与管理。

## 决定（Decision）

- 美术资源以 **AI 生成图片**产出，统一放在 `public/assets/` 下，按 `角色 / 卡面 / 图标 / 结局` 分目录。
- 代码**不直接引用图片路径**。资源通过一份清单（`src/content/assets.ts`）做 id → 路径映射，
  逻辑与组件只持有资源 id。
- 资源 id 缺失或文件不存在时，回退到程序化占位（CSS/SVG 绘制的色块 + 首字母），**禁止白屏或抛错**。
- 每张资源登记：id / 文件路径 / 用途 / 授权与来源备注（AI 生成需记录生成方式与日期）。

## 被否决的备选及原因（Alternatives considered）

- **纯程序化占位（CSS/SVG 绘制），不用位图**：零素材依赖、随代码演进、风格绝对统一。
  否决原因：观感上限明显，缺少《Reigns》那种手绘质感，首版就需要"看起来像个成品"的说服力。
  折中：**占位层仍然实现**，作为资源缺失时的兜底——它同时也是美术未就绪时的可玩保障。
- **组件里直接 `import avatar from './spidey.png'`**：最简单直接。
  否决原因：数百处硬编码路径后，换风格 / 换分辨率 / 换来源等于全仓改动；
  且无法做"资源缺失 → 占位"的统一降级。
- **预留接口，等真实素材**：避免做无用功。
  否决原因：会让视觉层长期缺位，UI 迭代时缺少真实约束，等到素材到位反而要大改布局。

## 后果（Consequences）

- 正面：资源可批量替换；缺失自动降级，任何阶段都能跑起来；来源可追溯。
- 负面：多一层间接（id → 清单 → 路径），调试时多跳一次；资源清单需要随内容同步维护，有腐烂风险
  （缓解：清单与卡牌同在 `src/content/`，且被完整性测试覆盖）。
- 后续要注意：`src/content/assets.ts` 是资源侧单一事实源，禁止在组件里写死任何图片路径。

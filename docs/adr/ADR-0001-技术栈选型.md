# ADR-0001：技术栈选型 —— TypeScript + Vite + React

## 背景（Context）

从零做一个《Reigns》式滑卡游戏。核心交互是「左右滑动出抉择 + 四指标实时反馈 + 大量随机事件」，
对以下三点有要求：① 滑动手势与过渡动画顺滑；② 卡牌内容量会到数百张，需要类型约束防止数据结构走形；
③ 核心玩法逻辑必须能脱离浏览器跑单元测试与平衡模拟（否则无法自动化验证数值）。

候选：TS+Vite+React / TS+Vite 无框架 / 单文件 HTML+原生 JS / Unity 或 Godot。

## 决定（Decision）

采用 **TypeScript（strict）+ Vite + React 18**，核心玩法逻辑放在 `src/core/` 且**零 React 依赖**。

- 类型系统承担第一道墙：`strict: true` + `noUncheckedIndexedAccess`。
- 测试用 Vitest，默认 `node` 环境（证明 `core` 不依赖浏览器），UI 测试按文件声明 `jsdom`。
- 卡牌内容用**类型化的 TS 常量**而非 JSON/YAML（见 ADR-0003）。

## 被否决的备选及原因（Alternatives considered）

- **TS + Vite 无框架**：依赖最少、包体最小，但动画与状态管理要手写，UI 迭代成本明显更高。
  否决原因：本项目首版要快速验证「手感」，UI 迭代速度优先于包体大小。
- **单文件 HTML + 原生 JS**：零构建、双击即玩，便于分享。
  否决原因：数百张卡 + 单元测试 + lint 的需求下，缺乏模块系统与类型会迅速失控；
  且工程化基建（本技能要求的「四道门」）要额外重搭。
- **Unity / Godot**：动画与多端发布能力最强。
  否决原因：C#/GDScript 下 AI 协作与测试基建成本更高，且本阶段不需要商业级动画。
  若未来确定要做商业手游，可重新评估（届时本 ADR 作废并新开 ADR）。

## 后果（Consequences）

- 正面：类型安全兜住内容数据结构；UI 迭代快；核心逻辑可无浏览器测试。
- 负面：引入 React 运行时与构建链，包体大于无框架方案；`core` 与 `ui` 的分层需要 lint 强制（不变量 #7）才能守住。
- 后续要注意：任何把 React / `window` / `localStorage` 引入 `src/core/` 的改动都会被 ESLint 拦截——
  这不是误报，是在守 ADR 的核心收益。
